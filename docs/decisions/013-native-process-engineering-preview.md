# ADR-013 · 本机进程构建与独立工程预览

## 状态与范围

2026-10-13：用户已明确选择“预览与下载对应同一工程，本机直接启动进程”，不要求容器调度。执行模式和 `workspace-build` 规格已确认，包含 V011 与有限构建预算；详细执行计划也已批准一次性实施，`app-runtime` / `runtime-access` 后续按既有模块边界设计。本文是设计决定，不是已实现声明；本轮不修改线上服务。

## 背景

现有平台与导出工程读取同一版本源码，并检查 SDK/文档模板一致性，但平台预览和独立应用使用两套宿主与数据后端。已完成的固定用例验收不能保证任意生成应用在两种环境下完全等价。

用户希望预览直接访问真实工程的运行实例，下载也来自该工程，而不是仅靠两套实现保持兼容。已有固定模板、构建脚本、独立 JAR 与 PostgreSQL 数据层可以复用；仓库的生命周期脚本目前是受信任验收工具，不能直接当作多项目生产管理接口。

## 决定

1. 继续使用现有五模块能力地图，不新增容器平台：先 `workspace-build`，再 `app-runtime`，最后 `runtime-access`。本机指运行平台后端的机器，不是每位网页访问者的电脑。
2. 本机模式仅运行平台白名单模板、固定依赖和经过原产物协议校验的 HTML/CSS/JS。模型内容不进入构建命令、包管理配置、Java 源码或路径；不支持用户上传任意工程、终端、自由依赖安装或模型生成后端。
3. 构建任务固定不可变工程快照和原始 ZIP，再在独立的新目录完整构建。记录 `sourceVersionId`、`sourceContentHash`、`bundleId`、`archiveSha256`、`loadedRuntimeId`、`jarSha256`；后续实例只能启动这个构建产物，预览下载只能返回该构建快照的 ZIP。
4. 构建由本机有限后台 Worker 执行，不占住 HTTP 请求线程，不放在数据库事务内。启动应用使用 Java 子进程，不通过 `sh -c` 拼接用户输入，不按占用端口杀进程。
5. 每个项目实例有独立工作目录、配置、端口、稳定安装 ID 和专用数据库/角色；升级同项目代码保留已有数据。管理员在机器上准备数据库资源，平台运行账号不默认获得 PostgreSQL 管理员权限。自动分配的具体契约由 `app-runtime` 规格定义，不在本轮偷偷创建数据库。
6. 私有预览访问由 `runtime-access` 负责，必须保持所有者鉴权、独立会话及来源隔离。不能只嵌入随机端口、放宽成通配 CORS、关闭 CSP 或把平台 Cookie 转发给独立应用。现有独立应用的 `frame-ancestors`/XFO 禁止嵌入，应通过明确的托管访问模式设计解决，而不是全局删除安全头。
7. 原平台 `/a/<slug>` 发布和 PREVIEW/LIVE 数据保持原样。新预览数据属于独立应用，不自动复制旧平台状态。过渡期两种预览必须明确标识；不能把旧预览作为构建失败后的无提示替代品。最终切换与历史只读行为由 `runtime-access` 规格定义。

## 进程与资源边界

不同目录、进程、端口不是操作系统级沙箱；同用户权限下，进程理论上可访问该用户的文件和网络。本方案只适用于当前固定可信模板的受控本地 Demo，不对不可信后端或公开多租户执行提供隔离保证。

进程管理要保留自有子进程句柄、启动身份和退出状态；不能只保存 PID 后随时 kill，因为 PID 会被复用。正常停止、超时、取消都需要等待退出，不能把“发出信号”当作停止完成。[Java 17 ProcessHandle](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/lang/ProcessHandle.html) 明确说明了 PID 复用和终止的异步性。

Node 的 POSIX detached 子进程可以形成独立进程组，但父进程退出不会自动保证子孙进程退出。因此需要受控监督器、父级连接断开检测及超时清理；不使用 nohup/unref 把任务放生。包装器被强杀或本机状态无法确认时，标记中断/需要核查，不扫描全机按名称或旧 PID 杀进程。[Node 24.20.0 子进程文档](https://nodejs.org/download/release/v24.20.0/docs/api/child_process.html#optionsdetached)

并发、超时、日志上限和磁盘准入检查用于保护本机体验，不冒充容器/cgroup 的 CPU、总内存或磁盘硬隔离。构建可以访问依赖仓库；不宣称通过环境变量过滤就隔离了文件系统或网络。

## 替代方案与后果

- 保持两套预览：改动小，但无法满足用户对实际运行产物一致性的要求，不作为最终目标。
- 容器执行器：适合以后支持不可信服务端代码与强资源限制，但本轮按用户选择不引入；原能力地图中的“必须容器”由本决定替代。
- 直接启动并返回端口：可作为管理员手动运行方式，但缺少归属、权限、退出监督与源码对应关系，不作为平台集成方案。

启用本机自动构建后，平台所在机器还需要 Node/npm、Java 17 工具链、可写专用工作根及专用构建测试库。现有“服务器运行平台包只需 Java/数据库”的部署说明对旧模式仍成立，不能据此宣称当前服务器已经满足新构建环境。

后续若开放任意后端/依赖、远程不可信用户执行或生产多租户托管，必须重新评审执行隔离与数据库供给，不沿用本机模式的安全结论。云端、GitHub 推送和真实模型调用仍需另行授权。
