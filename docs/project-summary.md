# Atoms Demo 项目实现说明

本项目围绕 AI 应用搭建平台的核心体验，实现“描述需求 → 智能体规划与生成 → 可交互预览 → 数据保存 → 继续修改 → 显式发布”的主流程。目标是交付一个能够真实调用模型、生成代码并运行应用的产品原型，而不是静态页面复刻，也不尝试在首版覆盖完整商业平台。

当前定位是**具备真实生成与持久化能力的受控 Web 应用搭建 Demo**。平台本身采用完整前后端架构；生成的应用则是受限 HTML/CSS/JavaScript 加平台数据 SDK，不是各自拥有独立后端、数据库和部署进程的完整工程。

说明基于 2026 年 10 月 11 日的本地代码与已有验收记录。云端记录截至 10 月 8 日；本轮状态修复与历史恢复尚未部署到演示站点。

- 源码：[GitHub 仓库](https://github.com/NigelWu95/atoms-demo)。
- 演示：[在线工作台](http://118.195.239.8:8443/)。当前使用明文 HTTP，仅用于临时演示，请勿输入敏感信息。
- 启动与部署：[项目 README](https://github.com/NigelWu95/atoms-demo/blob/main/README.md)、[服务器部署说明](https://github.com/NigelWu95/atoms-demo/blob/main/deploy/server/README.md)。

## 一 实现思路与关键取舍

### 先实现一条真实可用的核心流程

用户进入网站后建立访客会话，创建项目并提交需求。后端先把生成任务保存到数据库，再由后台 Worker 执行；页面通过 SSE 接收持久化的阶段事件。模型输出通过产物校验后，系统保存新的代码快照，并在工作台中加载交互预览。

应用中的待办、表单或游戏状态通过 SDK 保存到服务端，刷新后可以恢复。用户继续提出修改需求时，模型读取当前版本源码并生成新版本；失败不会覆盖旧版本。发布操作将公开链接绑定到指定版本，后续编辑不会自动改变线上版本。

这里区分三件事：模型完成输出、平台保存合规版本、应用实际满足用户需求。它们不是同一个成功标准。

### 技术栈优先服务于交付与一致性

前端使用 Vue 3、TypeScript、Vite 和 Pinia，承载首页、项目管理、对话工作台、源码视图和应用预览；后端使用 Java 17、Spring Boot、Spring Security 和 Spring Session，处理身份、授权、任务、版本及持久化。PostgreSQL 保存会话、项目、代码快照、运行事件、应用状态和模型调用记账，Flyway 管理增量迁移。

选择 Spring Boot + Vue，主要是契合既定技术偏好，并把事务、会话和任务管理放在一套清晰的工程内。首版没有足够证据表明更换为 Go 能提高交付成功率，因此不为语言本身增加迁移成本。未来如果执行服务需要独立扩容，可以沿现有接口拆分，并不要求先重写整个后端。

选择 PostgreSQL 的主要原因也不是免费，而是复用同一个关系数据库完成所有者隔离、幂等约束、修订号冲突检查和原子提交，减少额外组件。这里并不依赖 PostgreSQL 独有的 AI 能力，也没有给每个生成应用动态建表；其他关系数据库同样可以承载类似设计，但需要适配现有 SQL、锁和迁移。

### 用有界工作流表达 Agent 能力

生成流程由真实的 Planner、Builder 调用和程序校验组成：Planner 输出结构化计划，Builder 生成固定格式的完整应用产物；构建结果在 JSON 或产物契约校验失败时，最多额外调用一次修复。

这是一套可观察、可终止的编排流程，不是多个自主 Agent 自由协作。每轮通常需要两次模型请求，有限修复时最多三次；认证失败、请求超时和输出截断不进行盲目自动重试。SSE 展示的是实际任务阶段和结果，不是模拟进度，也不是模型逐 token 输出。

模型网关固定接入 DeepSeek，密钥只保存在服务端。开发阶段的 AI 编程助手用于辅助拆解需求、实现代码和编写测试；运行时的 DeepSeek 则用于响应平台用户的生成请求，两者用途和额度相互独立。

### 限定生成产物与执行范围

首版约定应用产物包含 manifest、HTML、CSS、JavaScript 和初始状态。生成代码在带有 sandbox 与 CSP 限制的 iframe 中运行，通过受限消息桥调用状态读写 SDK，不直接访问平台会话、数据库凭据或任意后端接口。

这一取舍省去了任意依赖安装、前端工程编译、服务器代码执行和容器调度，适合待办、计算器、表单草稿和小游戏等轻量应用。代价是不能直接生成任意 Vue/React 工程、安装 npm 包、连接任意外部服务或执行自定义后端逻辑。浏览器沙箱也不等同于进程隔离，不能承诺完全隔离恶意代码的 CPU、内存或导航行为。

### 将代码版本与业务数据分开

每次成功生成或修改都会保存不可变代码快照，应用业务状态则独立存储。这样可以保留版本历史，也避免一次代码更新直接清空已有数据。修订号检查防止旧页面静默覆盖新数据，幂等键用于确认同一次写操作，而不是无条件重复执行。

预览状态与公开应用状态分为 PREVIEW 和 LIVE，并按项目与访问者隔离。当前公开应用的不同访客各自保存数据，不是多人共享同一业务数据库；代码更新也没有通用的数据结构迁移能力。

### 访客身份降低体验门槛

首版采用服务端访客身份和持久会话，不要求用户先注册或配置 API Key。私有项目仍按所有者鉴权，不会因为知道项目地址就获得访问权限。

这一方案适合快速试用，但不能替代正式账号：清除 Cookie、更换浏览器或会话失效后，用户不能自行找回原访客项目。跨设备登录、OAuth 和访客转正式账号均留待后续。

### 单服务器部署与路径发布

部署采用 Nginx、Spring Boot 单实例和原生 PostgreSQL。Nginx 提供前端静态资源与 API 代理，已发布应用通过 `/a/<slug>` 访问；不为每个项目启动独立端口、容器、域名或 ngrok 进程。

这使部署包更容易在一台服务器上启动，也复用了预览、版本和数据能力。代价是平台与应用共享服务资源和故障范围，不能把项目级数据隔离描述为独立部署隔离。生成器目前只有一个 Worker，不支持直接增加多个后端实例来扩容。

## 二 当前完成程度

对照面向长期、多用户使用的完整 AI 应用搭建产品，当前已完成核心功能链路，但尚未完成全部端到端验收和生产化能力。功能实现、局部测试和线上完整验证分别记录，不用单一“完成百分比”概括。

### 已实现及其验证范围

| 能力 | 当前实现 | 已验证范围与边界 |
| --- | --- | --- |
| 网站与工作台 | 首页需求输入、项目列表与重命名、对话与预览布局、窄屏切换 | 已接真实后端，不是静态页面；未逐项复刻原产品全部 UI |
| 身份与权限 | 访客会话、项目所有者校验、CSRF 防护 | 已验证访客恢复与越权拒绝；没有正式注册登录或 OAuth |
| AI 生成 | DeepSeek 规划、构建、结构校验及一次有限修复 | 有真实模型成功案例；不是任意需求成功率保证 |
| 继续修改与版本 | 基于当前源码生成新快照、历史查看、恢复为新版本、失败保留旧版本 | 本地真实待办完成一次 V1 → V2 修改；固定产物回归验证恢复 V1 为 V3、数据与发布指针不变；第二轮真实连续修改仍待验收 |
| 预览与持久化 | 可交互 iframe、源码查看、独立私有预览、应用状态读写 | 本地待办和云端 2048 已验证操作保存及刷新恢复；不是通用数据库服务 |
| 预览检查 | JavaScript 语法解析、SDK 启动与运行错误观察、保存检查报告 | 本地回归通过；“检查通过”不等于功能正确或安全认证 |
| 发布应用 | 固定版本发布、显式更新与下线、稳定路径链接、独立公开页面 | 本地数据库与浏览器验证已覆盖；云端真实生成后的发布与 LIVE 全流程仍待验收 |
| 公开数据隔离 | LIVE 与 PREVIEW 分离、不同访客状态分离、更新保留数据 | 本地验证通过；不提供跨访客共享、业务角色权限或协作编辑 |
| 长任务与失败处理 | 任务持久化、SSE 回放、取消、分层超时、晚到结果保护、重启中断策略 | 云端生成中刷新恢复已通过；活动任务崩溃、整机重启等完整演练仍待完成 |
| 工程交付 | 构建脚本、配置模板、迁移、校验和、服务启动、备份与回退记录 | 已部署并上传源码；当前 HTTP 站点不代表生产安全上线 |

相比基础聊天生成，版本快照、持续修改、应用状态持久化、预览检查、固定版本发布和历史恢复已构成延展能力。历史恢复会创建新版本，保留原有历史与业务数据，不自动发布；旧代码的数据兼容性仍需使用者确认。

### 真实验收与质量现状

本地真实模型已完成“生成待办 → 新增和完成任务 → 刷新恢复 → 修改生成 V2 → 筛选且保留原数据”。云端真实模型已完成 2048 生成、生成中刷新后继续观察任务、游戏合并计分以及状态保存和刷新恢复。

最近一次发布构建通过了前端 106 项测试、后端 26 项单元测试、46 项 PostgreSQL 集成测试和 3 项打包测试，以及类型、lint、格式与构建检查。浏览器与真实模型验收单独记录；这些测试数量不代表所有产品场景都已覆盖。详细证据见 [验收记录](https://github.com/NigelWu95/atoms-demo/blob/main/docs/verification.md) 和 [云端部署记录](https://github.com/NigelWu95/atoms-demo/blob/main/docs/cloud-deployment.md)。

10 月 11 日本地增量验证通过：前端 112 项单元测试、后端 26 项单元测试与 50 项 PostgreSQL 集成测试、18 项运行时 Chrome 回归，以及类型、lint、格式和构建检查。修正了首页/列表固定显示“尚未生成”和首页过期生成提示；状态取自已保存的当前版本。未重新调用模型、打发布包或升级云端，不能把本地结果当作线上已生效。

真实调用也暴露了生成质量问题：一次构建在 16,840 tokens 上限下被截断，其中 16,266 tokens 用于推理，只有很少额度留给最终内容。当前部署已将单次上限设为 168,400 tokens，单次请求与整轮超时分别为 5 分钟和 10 分钟，累计调用上限为 100 次。额度包含推理与最终输出，次数上限也不是金额预算；提高 token 上限不保证所有应用都能完成。新额度已完成参数回归与部署检查，尚未据此重新完成真实生成验收。

### 尚未完成的产品能力

- **账号与协作**：正式注册登录、OAuth、跨设备恢复、组织与成员权限、实时协作。
- **完整开发环境**：多文件工程构建、依赖安装、终端、任意后端代码、独立应用数据库、应用级部署隔离和自定义域名。
- **迭代工具**：代码差异对比、可视化编辑、源码 ZIP 导出，以及把浏览器错误送回模型的一键修复。现有构建契约修复不等同于运行错误自动修复。
- **模型与商业化**：用户自定义模型/API Key、多供应商路由、按用户计费、充值订阅和完整费用预算。
- **生产保障**：公信 HTTPS、按身份限流、总存储配额、数据保留与删除策略、自动异地备份、完整监控告警、容量压测和多实例协调。

源码已上传 GitHub 属于项目交付，**不代表产品已经具备用户项目的 GitHub 授权、导入、导出或双向同步能力**。云端发布闭环、不同类型需求的生成质量和连续修改验收仍是交付收尾项，不应隐藏在后续功能计划中。

## 三 继续投入的扩展方向与优先级

优先级首先看是否影响核心流程成功、数据安全和费用可控，其次看是否改善用户持续使用，再考虑应用类型与商业化范围。新增能力应有明确验收场景，而不是只增加入口。

### P0 完成核心验收并控制开放风险

**首先补齐云端端到端验收。** 用明确的小额模型调用预算，走完新建、生成、交互保存、连续修改、发布、另一访客访问、刷新、更新发布和下线；同时验证活动生成期间取消、服务重启与连接中断。验收重点是旧版本不被失败覆盖、不因重复提交或重连而重复发起付费请求、状态不串项目，而不只是页面能打开。

**其次提高生成稳定性与成本可解释性。** 建立待办、计算器、表单等小型评测集，记录成功率、耗时、推理/最终输出消耗和修改后的数据保留情况。根据结果调整不同阶段的提示词、思考强度和 token 预算，向用户提供明确的失败原因与重试成本；不把持续提高上限或无限重试当作质量方案。

**扩大试用范围前补齐安全与运维底线。** 启用公信 HTTPS，增加身份/IP 频率限制、全局费用保护和项目/状态/报告配额；补上自动备份、恢复演练、任务失败与额度告警。这些事项优先于多模型和团队协作，因为公开访客可以直接消耗平台资源，而当前运行隔离和数据恢复能力仍有限。

### P1 改善留存与修改体验

**账号与访客升级。** 优先接入一种 OAuth 登录方式，设计已验证会话下的访客项目归属迁移、退出和跨设备恢复，解决用户换浏览器就失去入口的问题。

**差异查看与恢复增强。** 在已实现的历史快照恢复基础上补源码差异、数据兼容性提示和跨页面恢复意图保留；代码恢复仍不等于数据库回滚。

**错误辅助修复。** 将用户确认过的预览错误摘要作为新任务输入，仍受调用预算和修复次数约束。新版本必须重新运行检查，不能因为模型声称已修复就自动通过。

**源码导出与模型配置。** 先提供固定产物的 ZIP 导出，再考虑 GitHub 集成；先开放受控供应商选择与密钥安全存储，再考虑任意端点。两者分别改善产物可带走性和模型选择，但不应绕过既有所有者鉴权与费用边界。

### P2 扩展应用范围与服务规模

在轻量应用流程稳定后，再支持完整 Vue/React 工程、依赖安装和后端服务。届时需要引入独立构建与运行环境、资源配额、网络策略、镜像和依赖治理，并重新评估独立应用域名与发布生命周期。这是执行架构扩展，不是简单给每个项目分配一个端口。

多实例任务处理应先补任务租约、心跳、幂等领取与故障接管，再根据容量需求引入队列或独立 Worker。团队权限、协作编辑、计费订阅和应用模板市场则应在核心成功率、隔离与成本机制稳定后推进。

如果只继续投入一小段时间，我会优先交付一条可重复验证的云端完整流程、针对截断与修改失败的质量改进，以及最低限度的开放风险控制。它们直接决定这个 Demo 是否“可用、可信、可继续迭代”。
