# PR04：整页刷新后的生成请求恢复

状态：用户已于 2026-10-17 确认保存范围、整体实施计划及连续推进。实现与测试进度见 todo.md；实际验收结果见 verification.md，不继承前轮测试数字。

## 目标与当前事实

让用户在同一标签页刷新后仍能识别待确认的生成/修复提交，手动重试原请求，不产生新的操作编号，不把修复需求覆盖到普通需求草稿。

实施前 `frontend/src/stores/generation.ts` 仅在 Pinia 内存中保存 pending 和 repairRuns；跨路由保留，整页刷新丢失。本片扩展为经身份和项目校验的有界恢复，继续沿用原 key/body 重试未知结果，并通过 repairRuns 避免失败修复回填普通草稿。后端 `RunAdmissionService`、`IdempotencyService` 已按已认证所有者、资源、操作编号和请求摘要重放已提交结果；浏览器缓存不是权限或任务状态的权威来源。

## 范围与假设

- 覆盖用户已经点击提交的普通生成、继续修改和确认式修复，以及已接受修复的草稿保护标记；不保存尚未确认的修复面板输入或原始诊断。
- 仅保证同一浏览器标签页的刷新/页面恢复；不是跨设备同步、通用离线模式或任意关闭浏览器后的恢复保证。
- 保持当前 Java 17 / Spring Boot 3.5 / Vue 3 / TypeScript / Pinia；不新增依赖、后端接口或数据库迁移。
- 不改生成源码、模型配置、调用额度、工程下载或发布；不部署，不调用真实模型或发送邮件。

## 保存方式与取舍

使用专用 `sessionStorage` 键暂存最小恢复记录，不将请求正文写入 localStorage。sessionStorage 按 origin 与标签页分区，可以跨刷新保留；带 opener 的新窗口可能获得初始副本，因此不能把“标签页隔离”当作请求去重机制。浏览器也可能拒绝存储。[MDN 说明](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage)

记录需要：格式版本、保存时间、非认证的所有者 UUID/访客类型、项目 ID、已有账号变更通知的代次标记、原操作 key、完整原 CreateRun body、preserveDraft，以及已接受的修复 runId。不保存邮箱、显示名称、Cookie、CSRF token、API Key、完整聊天、应用数据、源码或原始报错；不把所有者 UUID 当成登录凭证。

**隐私取舍：需求正文可能包含敏感内容，保存到 sessionStorage 仍是浏览器可读缓存，不是加密存储，也不能抵御平台同源 XSS。** 这比当前“请求只在内存中”的范围有所扩大，用户已确认本片保存范围。使用场景和保存期限必须在提交/恢复提示中明确。

实现上限：恢复有效期 24 小时，同一标签页最多 10 个项目记录，序列化总长度不超过 256000 个 UTF-16 代码单元，单个 prompt 沿用接口 1–8000 字符限制。刷新、读取或重试不能延长原有效期。活动页面到期清理请求正文，恢复页面时先处理过期记录；不承诺页面关闭期间能物理清除浏览器磁盘上的数据。

不静默挤掉尚未确认的请求。遇到过期、损坏或存储不可用，显示明确的恢复不可用提示，禁止自动补造请求或操作编号；允许用户核对任务历史后明确放弃本地恢复记录。放弃记录不表示服务端任务被取消，重新提交是新操作且可能计费。缓存写入失败时保留现有内存精确重试能力，并提示刷新后无法保证恢复。

替代方案：服务端持久化“提交意图”可以避免浏览器持有完整请求并支持跨设备，但需要新资源、保存期限和数据库迁移，不在本片实现。单纯只缓存操作 key 不能重试未到达服务端的请求，因为现有接口还要求完整原 body。

## 恢复与交互规则

1. 首次提交前捕获不可变的原请求及 key；只有用户实际确认的请求可以进入恢复记录。准备修复、打开页面和页面刷新均不得提交生成请求。
2. 初始化先完成真实身份校验和项目归属读取，再恢复同一所有者、项目和账号变更代次的记录；验证前不显示缓存正文。缓存值须按固定字段、类型、长度、枚举、ID 格式和安全整数校验，不执行缓存中的代码。
3. 未知结果显示“上次提交结果待确认”，可审阅原需求、版本基线及保存时间；用户点击后发送完全相同的 key/body。不得把用户新输入或当前新版本拼到旧请求中。
4. 文案应说明：若上次已经提交成功，服务端返回原任务；若上次从未到达服务端，本次重试可能创建任务并消耗模型额度。不能把 POST 重试描述成“只查询，不计费”。
5. 获取已接受结果后清除 pending 正文；若是修复，保留最小 runId 草稿保护标记，在有效期内刷新仍不把失败修复需求填回空白草稿。原有非空草稿始终不覆盖。
6. 已知拒绝沿用原错误处理，不自动更换 key 重试；无法判断结果时继续保留原请求。新版本导致旧基线冲突时展示服务端结果，不能替换成新基线偷偷提交。
7. 退出、身份失效、访客升级和账号切换清理本标签页缓存；其他标签页继续使用原账号变更通知。后台恢复页面先重验身份与变更标记，迟到响应不能复活已清除记录。
8. 标签页复制产生的相同请求仍依赖服务器幂等，不能因复制而生成新的 key。不同项目分别恢复，不提供跨标签页自动同步请求正文。

## 验收标准与测试策略

- 单测先复现：新建 Pinia/整页重建后 pending 和修复标记丢失；实现后精确恢复、原 body/key 不变、有效期不延长。
- 安全单测：身份未确认、所有者不匹配、账号代次变化、缓存篡改、超长/过期/损坏数据、存储读写异常、迟到响应均不能触发提交或泄露旧正文。
- 组合回归：普通请求与修复分别覆盖，非空和空草稿、成功/拒绝/未知结果、账号切换、项目切换、重复点击、跨路由及整页刷新；恢复提示期间不能绕过旧 pending 创建新任务。
- 隔离 Chrome 用受控提交边界验证 POST 次数、key/body 精确相等，以及真正的 `page.reload()` 后手动恢复；不能只用组件重挂冒充浏览器刷新。服务端已提交响应丢失的场景，应验证重复确认返回同一任务而不是创建第二条。
- 手机和桌面、键盘操作、读屏状态、axe、控制台与现有邮箱/生成/工程下载回归不降低标准。不得用替身测试宣称真实模型修复成功率。
- 完成时更新实际验收记录和能力说明，明确缓存范围、隐私风险、失败降级和未部署状态。

## 边界

- 始终：缓存视为不可信输入；真实身份和所有权由服务端确认；用户手动确认，原 key/body 精确重放；维护原草稿和已有错误处理。
- 先确认：浏览器暂存请求正文的隐私取舍；新 API/数据库迁移、认证语义调整、新依赖、真实付费调用或部署。
- 禁止：浏览器保存认证凭据；自动重新生成；缓存清理冒充取消服务端任务；关闭权限/幂等校验；提交私有配置、验证码或真实用户请求。
