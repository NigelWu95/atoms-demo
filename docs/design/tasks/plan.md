# Atoms Demo · 分阶段开发计划

日期：2026-10-07。状态：实施中，T01–T03、T05–T19 已通过相应本地验收；真实 DeepSeek 生成、应用数据保存及一次修改保留数据的 C10 闭环通过。Java 按用户要求固定 17.0.5-oracle；累计调用 11 次真实模型，当前授权剩余 0，未部署公网服务。T24 的两轮修改及 T31 多类型质量验收仍未完成；未完成阶段仍是目标，不是已有能力。

## 1. 目标与执行入口

交付一个真实可用的闭环：进入网站 → 创建项目 → 自然语言生成代码 → 操作预览并保存数据 → 继续修改 → 显式发布 → 通过公开链接访问。优先延展能力为历史版本恢复。

依据：[功能设计](../02-functional-design.md)、[架构设计](../03-architecture.md)、[接口契约](../04-api-contracts.md)。详细任务及进度唯一记录在 [todo.md](todo.md)，本文件负责顺序、边界、检查点、风险与排期。

本计划使用 agent-skills 的 planning-and-task-breakdown 拆分依赖与验收，以 incremental-implementation 组织小步交付。每个阶段尽快接通页面、接口和数据，不把所有页面或所有后端完成后才统一联调。

### 开工假设

| 项目 | 当前默认 | 如何落定 |
|---|---|---|
| 后端 | Java 17、Spring Boot、Spring JDBC、Flyway | T00 锁定已验证版本，不为“最新”临时升级 |
| 前端 | Vue 3、TypeScript、Vite、Router、Pinia | T00 检查 Node 与所选脚手架兼容性 |
| 数据库 | PostgreSQL | 若已有熟悉的 MySQL 环境，可在 T00 一次性改用 MySQL；只实现和测试一种 |
| 模型 | DeepSeek 官方 deepseek-flash，服务端 ModelGateway 适配 | 已完成真实生成、保存和一次修改；多轮/多类型质量待验证 |
| 部署 | 单实例后端、同域前端/API、数据库持久卷、HTTPS | T00 确认资源，T04 提前部署骨架 |
| 生成范围 | HTML/CSS/经典 JavaScript + 平台数据 SDK | 不生成独立后端，不接任意 npm 安装 |
| 身份 | 持久化访客会话 | 注册登录为增强项，不阻塞首次体验 |

PostgreSQL 不是技术硬依赖，也不是因为“只有它免费”。本计划不使用向量检索等特有能力作为前提。若改 MySQL，需同步修改驱动、迁移、JSON 类型、行锁/任务领取 SQL、会话表和集成测试；不要一边开发一边维护双数据库兼容层。

模型密钥已由用户本地配置并完成实际请求，累计上限 6、已用 5。服务器或域名仍未落实；在线验收不能在缺少资源时标记完成。Atoms 赠送额度不等于自建 Demo 的 API 额度。

本轮按用户希望优先推进主功能的要求，M4/M5 交错实施：后台工作流和工作台先通过短轮询形成可交互入口，再补 T20 SSE；不是放弃事件契约，也不把阶段轮询描述为流式输出。详见 ADR-006。

## 2. 范围与不做事项

P0 对应功能 F01–F13，包含真实模型生成、取消/异常、刷新恢复、版本快照、应用数据保存、公开访问、基础隔离和上线验证。P1 首选历史恢复；错误辅助修复、注册登录、源码导出不计入基础冲刺承诺。

首版不引入 Redis、消息中间件、微服务、向量库、任意命令执行、容器化生成应用、OAuth、支付、团队空间、可视化点选编辑或 Monaco。生成器和验证器不得用模板静默接管模型失败。

开发预览允许使用明确标注的固定测试产物；它只能存在于测试夹具或开发配置中，不能作为生产生成入口的成功结果。

## 4. 8 小时冲刺时间盒

以下是时间分配目标，不是经过实测的工作量承诺。T00–T35 共 36 个执行任务，其中 34 个为 P0/交付任务、2 个为优先 P1；另有 T36–T41 六个可选任务。它们是验收单位，不代表每项只需要几分钟。

在熟悉 Java/Vue、已有脚手架、模型和服务器就绪、AI 辅助顺利的条件下，可尝试以下时间盒。从零搭建所有安全/一致性机制时很可能超出 8 小时，应如实记录，不能把环境调试和测试排除在总工时外。

| 目标时段 | 内容 | 超时后的处理 |
|---|---|---|
| 00:00–00:20 | M0：资源、模型最小请求、版本冻结 | 模型或部署资源缺失立即记录，请用户提供；不宣称已打通 |
| 00:20–00:55 | M1：基础网站、构建、部署骨架 | 停止视觉细节，只保留首页和工作台基础布局 |
| 00:55–01:30 | M2：真实会话与项目 | 不增加账号、文件夹、搜索等额外管理功能 |
| 01:30–02:35 | M3：预览、SDK、业务数据 | 这是高风险门槛；未通过前不包装成生成成功 |
| 02:35–04:05 | M4：真实生成与任务控制 | 只接一个供应商，保留有限修复与明确失败 |
| 04:05–04:40 | M5：工作台联调 | 只读源码，不加复杂编辑器和动画 |
| 04:40–05:20 | M6：发布和公开访问 | 同域路径发布，不做自定义域名或独立容器 |
| 05:20–06:00 | M7：完整应用上线与烟测 | 发现 P0 缺陷，后续时间优先用于修复 |
| 06:00–06:40 | M8：历史恢复，或修复 P0 | 仅在 P0 稳定时实施；不启动其他增强任务 |
| 06:40–08:00 | M9：回归、修复缓冲、文档、录屏 | 冻结新功能；最终至少保留 20 分钟整理提交材料 |

第六小时是“完整功能候选版本”的检查点，不等于已经通过全部交付验收。若实际只能开发 6 小时，至少预留最后 45 分钟做最终验收与提交，取消 M8；若 P0 仍未完成，应报告真实缺口，不能以演示替代实现。

48 小时是提交窗口，不把它理解成可以悄悄扩展为 48 小时开发。记录实际专注工时；发生资源等待时也记录等待原因。

## 6. 统一完成标准

按 agent-skills 的 Definition of Done 调整为本项目标准，所有任务共用，不因时间紧而降低：

1. 验收条件逐项通过；涉及用户行为必须有运行时证据，编译成功不等于功能完成。
2. 业务逻辑有可重复测试；新增的越权、取消竞态、状态冲突和发布边界必须覆盖失败路径。测试替身不能算真实生成实测。
3. 本阶段相关构建、类型检查、测试通过；不通过删除断言、跳过失败测试或关闭检查伪造通过。
4. 错误对用户可见；日志可关联 requestId/runId/stage，不记录密钥和完整业务数据。
5. 迁移可从空库应用；已运行库用增量迁移，不修改已执行迁移。破坏性重置和删卷不属于修复手段。
6. 模型凭据只在后端；私有资源按所有者鉴权；不可信代码仅运行于受限文档。
7. 文档与真实功能一致，记录验证命令、结果和已知限制；未实测项保持未完成。
8. 合并、付费资源创建、公网部署等按实际用户授权执行；本计划本身不授权开通云资源、发送消息、推送代码或生产变更。

检查点要求运行相关测试和构建、演示刚完成的切片，并向用户汇报证据。无需把每个内部检查点变成无条件的人工等待；涉及范围变更、额外付费或新外部权限时再停下确认。

## 8. 风险与处理

| 风险 | 尽早发现的位置 | 处理与禁止事项 |
|---|---|---|
| 依赖/Node/JDK 不兼容 | T00–T02 | 锁定已验证组合；不自动升级用户机器的全局环境 |
| 供应商协议不兼容或无额度 | T00、T17 | 小请求核验；明确失败，禁止伪造生成或盲目重试 |
| CSP/反代叠加导致页面不运行 | T04、T11–T14 | 在真实浏览器检查响应头；不得放宽整个管理站点的策略 |
| SSE 被缓存、部署休眠 | T04、T20、T29 | 提前验证长期进程与流式响应；不等最终录屏才排查 |
| 模型修改破坏已有数据结构 | T18、T24、T31 | SDK 契约约束、兼容性测试；不把清空数据当作修复 |
| 取消与保存竞态 | T19、T21 | 同锁次序、短事务、提交前重新核对；不在事务里等待模型 |
| 幂等/状态版本冲突 | T07、T13、T16、T26 | 数据库唯一约束与 CAS，冲突明确返回，不静默覆盖 |
| 访客滥用生成费用 | T22 | 全局预算、并发、队列和输出上限；Cookie 限额不算充分防护 |
| 6–8 小时不够 | 每个检查点 | 取消 P1 和视觉装饰；不删持久化/隔离/实测来宣称达标 |

iframe 方案不是通用恶意代码执行云，也不能保证隔离 CPU 卡死或封锁浏览器所有网络能力。保持小规模受控 Demo 边界；扩大开放范围前另立独立运行域和资源隔离任务。

## 9. 执行方式与后续技能

每次只领一个任务或一个相邻的小切片：读依赖与现有代码 → 先明确验证 → 最小实现 → 定向测试 → 更新证据与清单 → 到检查点做集成回归。不得把“代码生成好了”直接写成“功能已完成”。

后续按实际任务使用对应 agent-skills，而非一次性加载所有技能：

- 基础页面与工作台：frontend-ui-engineering；真实浏览器验证使用可用的浏览器测试工具。
- 接口与状态契约：api-and-interface-design；不改动已冻结契约时直接遵循现有文档。
- 业务实现：incremental-implementation、test-driven-development；接口、会话、沙箱和数据边界使用 security-and-hardening。
- 故障：debugging-and-error-recovery；不随机更换架构掩盖根因。
