# 05 · 6–8 小时交付计划与验收

本计划是目标排期，不是已完成进度。开发者需熟悉所选技术栈，并有可用模型 API 与部署环境。若上述条件不具备，先记录阻塞与实际耗时，不能把环境准备从总投入中隐去。

实施顺序以 [详细开发计划](tasks/plan.md) 和 [任务清单](tasks/todo.md) 为准。本文保留冲刺预算、验收用例和提交要求，不单独维护另一套任务进度。

## 1. 开工条件

开始计时后的第一步确认：

- 模型端点、模型 ID、密钥已在服务端环境配置，可以完成小请求和取消/超时测试。
- 所选数据库与本地 Java、Node、构建工具可用；依赖版本锁定。默认 PostgreSQL，可在开工时改为熟悉的 MySQL，但不同时实现两套。
- 部署目标支持持续运行的后端、SSE 和持久化数据库，域名/HTTPS 有落地路径。
- 确定首版使用 web-static-v1 产物，而非临时扩大到任意前后端构建。
- 本文档的默认选择可开工；模型供应商和服务器仍需根据实际资源落定。

用户提供的 Atoms 额度可用于观察参考产品；不假定能用于自建 API 请求。无需以完成参考产品的所有高级体验为前置条件。

## 2. 前六小时：完整候选版本目标

| 时段 | 交付切片 | 通过条件 |
|---|---|---|
| 00:00–00:20 | M0 环境与资源冻结 | 模型最小请求、工具版本和部署条件有证据 |
| 00:20–00:55 | M1 基础网站与提前部署 | 首页、工作台骨架、健康检查可访问 |
| 00:55–01:30 | M2 会话与项目闭环 | 新建、打开、重命名、刷新恢复和身份隔离 |
| 01:30–02:35 | M3 受限预览与数据存储 | 标注为测试产物的应用可运行、保存、刷新 |
| 02:35–04:05 | M4 真实生成、任务与 SSE | 产物来自真实模型；取消、异常和重连有明确行为 |
| 04:05–04:40 | M5 对话工作台与修改 | 用户通过网页生成、修改、查看源码与错误 |

这张表是熟悉技术且资源就绪情况下的激进时间盒，不是完整工作量的实测估计。第六小时的候选版本不等于通过最终验收；不要等到最后半小时才首次部署。实际落后时裁剪增强项和视觉细节，保留题目硬要求与关键数据边界。若只能投入六小时，至少留最后 45 分钟验收和提交；P0 未完成就如实报告，不能跳过验证宣称交付。

## 3. 第七至第八小时

| 时段 | 首选工作 | 退出条件 |
|---|---|---|
| 06:00–06:40 | M8：P0 稳定则做版本恢复，否则修复 P0 | V1 → V2 → 恢复 V3，原版本与数据保留；或关键缺陷得到修复 |
| 06:40–07:40 | M9：冻结功能、最终回归、修复缓冲、准备演示 | 最终版本通过适用验收，证据与实际功能一致 |
| 07:40–08:00 | M9：外部复核、录屏/提交材料收尾 | 实际 URL、源码、说明与演示齐全 |

如果第六小时仍有 P0 缺陷，第七小时先修复；版本恢复不得以破坏原版本或删除失败测试为代价。8 小时内未交付的功能如实标注，不宣称已经实现。

## 4. 详细开发任务入口

开发任务集中记录在 [tasks/todo.md](tasks/todo.md)，编号为 T00–T41，取代之前的八个粗粒度任务；当前执行进度见任务清单，未勾选项保持待实施。

- T00–T09：开工准备、网站骨架、真实会话与项目。
- T10–T15：不可变快照、受限文档、SDK、应用数据、源码查看。
- T16–T25：真实模型、可靠任务、SSE、取消、预算、对话修改与预览检查。
- T26–T31：发布、公开状态、线上部署、安全与真实生成验证。
- T32–T33：优先延展——历史恢复。
- T34–T35：最终回归、录屏与提交。
- T36–T41：可选错误修复、账号、源码导出，不计入基础八小时承诺。

每个任务包含具体依赖、主要文件、至多三条验收条件和验证方式；每 2–3 个任务设检查点。详细风险、技术冻结和统一完成标准见 [tasks/plan.md](tasks/plan.md)。

## 5. 时间不足时的裁剪顺序

先去掉 Race Mode、上传、可视化点选、完整代码编辑器、GitHub、完整认证与主题管理；它们原本就在 P1/P2。接着缩减动画、示例数量、项目卡片装饰和非核心筛选。

必须保留：真实模型生成、真实交互、可恢复的数据、清楚失败状态、基本隔离、在线访问和可复现主流程。不能把模板切换、聊天回复或静态图片包装成已经交付的核心能力。

生成应用业务状态属于本方案主动选择的质量目标；若它迟迟无法实现，需要明确改为“只持久化平台项目与版本”，同步调整文档、演示与说明，而不能保持原承诺却退回 localStorage 冒充服务端存储。

## 6. 关键验收用例

| 编号 | 操作 | 预期结果 |
|---|---|---|
| A01 | 无历史会话进入首页并提交提示 | 初始化身份、创建项目、真实生成 |
| A02 | 生成待办并新增两条任务，刷新 | 两条任务恢复，保存状态正确 |
| A03 | 再要求增加筛选 | 出现新功能，原操作和数据保留 |
| A04 | 在生成期间刷新工作台 | 恢复 run 状态，不再创建第二个任务 |
| A05 | 同一请求键重复提交 | 同一 runId，模型调用不因客户端重试重复 |
| A06 | 使用同一键提交不同请求体 | 422，明确指出误用 |
| A07 | 停止一轮生成后等待上游返回 | 保留旧版本，晚到结果不成为当前版本 |
| A08 | 模型返回错误结构或超时 | 明确失败，有限修复，无无限转圈 |
| A09 | 注入一个语法错误测试产物 | 显示预览错误，源码可查看，不伪报通过 |
| A10 | 创建者发布 V1，再生成 V2 | 公开链接仍展示 V1 |
| A11 | 发布 V2 后刷新公开链接 | 显示 V2，当前访问者原数据保留 |
| A12 | 两个独立浏览器访问同一应用 | 各自状态隔离 |
| A13 | 两标签对相同 revision 写不同数据 | 一个成功，一个收到冲突，不静默覆盖 |
| A14 | 猜测另一用户项目/版本/run ID | 无法读取私有信息 |
| A15 | 预览尝试访问宿主 DOM、Cookie、任意 API | 隔离或接口拒绝，不暴露平台凭据 |
| A16 | 直接打开运行 document URL | HTTP CSP sandbox 仍生效 |
| A17 | 切换 iframe 后旧消息继续返回 | 旧通道失效，不影响当前版本 |
| A18 | 重启应用容器 | 项目、版本、状态和有效会话仍在；中断运行有终态 |
| A19 | 手机宽度与桌面宽度操作生成应用 | 核心按钮和表单可用，无关键内容遮挡 |
| A20 | P1 从 V1 恢复 | 新 V3，V2 保留，不重置数据、不自动上线 |

测试分配：状态与权限使用后端集成测试；桥接和错误态使用前端测试；主要流程使用真实浏览器 E2E；真实模型质量使用受限次数实测。无需为文案和装饰建立大量脆弱快照测试。

## 7. 建议的三分钟演示

1. 打开首页，输入“做一个个人任务管理工具，有新增、完成、筛选，数据刷新后保留”。
2. 展示 Planner 摘要、Builder 真实进度和产物版本。
3. 预览中添加两条任务、完成一条，刷新证明持久化。
4. 追加“增加优先级选项和筛选”，展示代码变化与新版。
5. 若已完成 P1，恢复历史源码并说明数据没有回滚。
6. 发布，复制 URL，用无痕窗口打开并操作；说明访客数据独立。
7. 用一句话解释边界：平台用 Java/Vue，生成应用为受限 Web 代码，未来可接入编译/容器运行器。

模型等待可能使现场超过三分钟：准备一份明确标注的历史生成项目用于展示版本和发布，同时保留真实新生成入口；不能将预录结果冒充刚刚生成。

## 9. 成本与可用性

生成成本近似为各模型调用的输入/输出 token 费用之和，另加服务器与数据库费用。首次生成通常包含规划和构建两次调用，失败修复最多再加一次；价格必须依据实际供应商确认。

公开 Demo 设置全局生成预算、并发上限和每轮输出上限。保留样例项目用于模型短时不可用时查看既有成果，同时明确新生成不可用状态。不要把 Atoms 赠送额度折算为自建模型 API 预算。

## 10. 后续实施需落定的选择

1. 实际模型供应商和可用模型 ID。
2. 已有服务器、域名或托管平台。
3. 保持推荐的“生成前端 + 平台数据服务”，还是明确升级到独立全栈应用生成。
4. Java 与 Go 的实际熟练度是否足以改变默认选型。

这些不会阻止本设计文档完成；真实接入与部署阶段必须有对应资源，不能虚构已可使用的账号或在线链接。
