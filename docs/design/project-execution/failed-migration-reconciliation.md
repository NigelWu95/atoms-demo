# 失败迁移后的显式核对与恢复

状态：2026-10-26，用户回复“继续”，确认实施本方案；EX27c1 的两个真实应用成功升级与重启验收已通过，见[记录](../../project-execution-verification.md#2026-10-26--ex27c1-双应用-v2-升级与重启)。本方案新增维护者显式确认边界，不把原来的待核对记录自动改为终态；实现与验收按下列分片记录。

## 问题与范围

当前应用在持久 READY 之前退出时，即使原 worker 已取得并保存准确停止收据，仍会留下 `NEEDS_RECONCILIATION`，因为停止进程不能证明数据库没有部分改变。协调器因此停止新的调度并保留资源。现有行为正确保留了不确定性，但缺少核对后恢复工作的内部入口。

仅支持本次原协调器仍持有资源、实际 worker 已退出且数据库已持久保存 `execution_pending=false` 和停止摘要的启动失败。仍未取得停止证明、提交结果不明、失去协调租约或 JVM 重启后遗留的记录不在本次范围内；尤其不处理原有五份未决审计。初版仅提供可信维护者内部接口，不增加网页、任意 SQL、终端或按 PID 停止能力。

## 用户可观察行为

1. 启动失败后仍显示失败原因及需要核对，不自动重试、回退 SQL 或启动旧 JAR。
2. 维护者读取固定运行的构建/源码/绑定身份、原停止记录及当前迁移历史摘要。
3. 维护者明确确认“接受当前数据库状态”，提供刚读取的准确运行和历史摘要。
4. 确认成功后记录独立审计，将该运行结束为 `FAILED`，保留原错误、源码、JAR、执行身份和停止摘要。
5. 原协调器只释放已经完成的资源，不继续复用已经停止的 executor。新协调器正常启动后，下一次运行仍经过原迁移兼容性与批准检查。

确认不等于数据回滚，也不证明任意 SQL 没有改动业务行。真实验收样本会另外比较历史、表结构与原待办数据，但通用产品接口不作此承诺。

## 内部契约

`inspectStoppedFailure(owner, project, run)` 返回不可用于停止进程的只读说明：运行/执行/构建/源码/绑定 UUID、树/JAR/停止摘要、当前迁移历史摘要和固定失败码。返回前核对当前维护者、项目归属、原协调租约与执行根、目标物理数据库身份和原封存来源。文件及业务库读取不占用平台元数据事务。

`acknowledgeStoppedFailure(owner, project, run, expectedView, idempotencyKey)` 只接受准确快照和显式接受当前数据的动作。短事务按原项目→运行顺序锁定，重新检查原身份、待核对状态、pending=false 和停止摘要，写入追加审计并结束失败运行。相同确认返回原审计；不同快照拒绝；不重放提交结果不明的事务。历史变化要求重新读取并确认。

该流程不从摘要重建 `Stopped` 对象，也不调用进程停止 API。摘要只引用原 worker 已保存的历史事实。协调器只有在原执行线程结束、未再持有任何未知进程、确认审计准确匹配对应 job 后，才移除该已完成 job 并执行原关闭流程；不能清空其他任务或释放未知资源。

新增追加式 `execution_run_reconciliations` 元数据表，保存确认人、运行及停止身份、绑定、原错误、确认时历史摘要和时间。迁移追加新编号，不修改 V028/V029；旧运行事件和已应用业务迁移均不改写。业务库不执行 clean、repair、删表或恢复备份。

## 原生失败迁移验收

使用已经获准的 A 项目及原 A 业务库/端口。保留 V2 构建，追加一个源码版本，仅增加事务性迁移：先建临时测试表，再触发确定 SQL 错误；沿用原依赖和真实 npm/Maven 构建。准确批准该新迁移后启动，预期真实 Flyway 失败且运行进入待核对。

在不确认的情况下证明新准入被拒绝；用原实际停止记录和只读数据库检查完成确认，证明无自动数据回滚声明。样本额外检查迁移历史、临时表不存在和原行值不变。将已评审 V2 文件通过原编辑网关追加为新的源码版本，保留失败版本，不能移动或删除历史 Git ref。原协调器结束后，新协调器按常规规则启动兼容构建，核对原数据及源码/JAR 身份。

不新建数据库、角色、项目绑定，不修改私有 env、全局工具配置或日常实例，不调用真实模型/SMTP，不推送或部署。
